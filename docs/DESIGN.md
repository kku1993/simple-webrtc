# simple-peer Signaling Server

This is a simple signaling server designed to work with the
[simple-peer](https://github.com/feross/simple-peer) WebRTC client library.

## Terminology

- Room
  - Room consists of 2 clients - the host, who created the room, and the guest,
    who is joining
  - Each room holds 2 websocket connections - one for host, one for guest
  - To create multiple peer connections, the client needs to create separate
    room for each pair of peers.

## Transport

Allow communication happens over WebSocket with JSON text payload.

The URL path to use is `/v1/rooms/<roomId>/ws`, where `roomId` is randomly
generated by the host client **before** creating the room (for reason, see
horizontal scaling section below).

## Websocket methods

- CreateRoom
    - Initiated by the host client to create a new room
    - Request:

        ```typescript
        {
          type: "create-room";
          guestPassword: string | undefined;

          // Optional: enforced by servers with Cloudflare turnstile check
          // enabled
          cloudflareTurnstileToken: string | undefined;
        }
        ```

    - Success response:

        ```typescript
        {
          type: "create-room-response";
          rejoinToken: string;
          timeoutAt: string;  // ISO timestamp
        }
        ```

    - The `timeoutAt` field indicates the time at which backend will clean up
      this room if no guest has connected to the room by then. Client should
      display this information to the user. By default, set to 10 minutes from 
      the time of room creation.

- JoinRoom
    - Initiated by the guest client to join a room
    - Request:

        ```typescript
        {
          type: "join-room";
          roomId: string;
          guestPassword: string | undefined;
        }
        ```

    - Success response:

        ```typescript
        {
          type: "join-room-response";
          rejoinToken: string;
          roomId: string;
        }
        ```

    - Backend should also send a message to the host client

        ```typescript
        {
          type: "guest-joined";
        }
        ```

    - Once a room has 2 clients connected, no new clients can join. Rejoins must
      be done by presenting the `rejoinToken` (see below)

- RejoinRoom
    - If either client disconnects, they can rejoin the room by presenting their
      rejoin token
    - Request:

        ```typescript
        {
          type: "rejoin-room":
          roomId: string;
          rejoinToken: string;
        }
        ```

    - Success response:

        ```typescript
        {
          type: "rejoin-room-response";
        }
        ```

- Signal
    - Initiated by either the host or guest client to send signaling data to
      the other client through an established room
    - Request:

        ```typescript
        {
          type: "signal";
          data: string;  // JSON stringified
          signaledAt: string;  // ISO timestamp
        }
        ```

    - Upon receiving this request, backend should send the follow message to the
      receiving client

        ```typescript
        {
          type: "signal-response";
          data: string;  // JSON stringified
          signaledAt: string;  // ISO timestamp
        }
        ```

    - In case the receiving client has disconnected, backend should store the
      latest signal message and resend it whent the client reconnects.

## Data persistence

All data is only stored in memory - this means that if a signaling server
instance crashes, we lose all the state.

Clients should implement retry logic to recreate room (on host side) and
rejoin room (on guest side) to handle this.

## Horizontal scaling

If deploying multiple copies of the server behind a load balancer, clients
should configure the loadbalancer to perform session affinity based on HTTP
cookie, because browser websocket API doesn't allow setting custom HTTP header.

This is why we require the host client to generate the `roomId` up front - it
needs to be included in the initial `CreateRoom` request to make sure it gets
routed in the same way as the subsequent `JoinRoom` request from the guest.
Also, HTTP cookies are scoped by path, so including the `roomId` in the URL path
helps in the case where the browser is connecting to different rooms.

## Room timeout

In addition to the `timeoutAt` field in `create-room-response`, enfroce a global
timeout of 90 minutes - force shutdown a room 90 minutes after creation.

Leave a tombstone in memory for up to 2 days so subsequent attempts to join the
room will get a unique error code indicating the room is closed and the client
should open a new room. This is best effort of course.

## Bot prevention

If configured with Cloudflare turnstile key, server should require `create-room`
requests to come with a token for validation.

## Security

- Limit all websocket JSON payloads to 512 kb
- Have a in-memory client IP rate limit of 2 requests / second. Respect
  `X-Forwarded-For` or `X-Client-Ip` headers ONLY if configured to do so.
